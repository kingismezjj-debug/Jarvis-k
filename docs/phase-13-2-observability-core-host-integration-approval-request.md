# Phase 13.2 Observability Core Host Integration Approval Request

Recorded on 2026-08-05 after the Phase 13.1 provider-neutral Observability
contract landed and CI passed.

## Status

`APPROVED_IMPLEMENTATION_SCOPE`

This request is for a narrow Core Host integration implementation wave. It
does not authorize a runtime/cache window, real artifact access, helper
execution, Memory route execution, persistent telemetry, UI/IPC exposure, or
any change to the frozen Model Lifecycle alpha.

## Context

Phase 13.1 added:

- strict provider-neutral Observability schemas in `@jarvis-k/contracts`;
- a pure in-memory collector, sanitizer, and fixed failure classifier in
  `@jarvis-k/capabilities`;
- fixture-only coverage for normal, degraded, blocked, timeout,
  cancellation, rollback, and cleanup outcomes; and
- no changes to `apps/core-host`, runtime packages, Memory, Desktop, UI, or
  release behavior.

Phase 13.2 is the proposed approval boundary for wiring Core Host code to
create Observability observations from already-sanitized lifecycle/helper
report-shaped values. The integration should make future developer-alpha
diagnostics easier to inspect, but it must remain inert unless a caller
explicitly constructs and uses the integration in tests or an already approved
diagnostic path.

## Exact Scope Requested

Approve one implementation wave for:

- Core Host adapter functions that map existing sanitized lifecycle/helper
  report-shaped values into Phase 13.1 `ObservabilityObservation` DTOs;
- a small in-memory Core Host observation session wrapper around the Phase
  13.1 collector;
- fixed mapping from lifecycle report fields to phase/status/activation,
  preservation, rollback, cleanup, reason-code, stop-reason, and failure-class
  values;
- fixed mapping from helper health/load/release outcomes to
  health/load/release states and stop reasons;
- correlation-id validation using the Phase 13.1 bounded opaque ID rules;
- fail-closed behavior for unknown status, unknown reason code, unrecognized
  report shape, sensitive field, out-of-bounds collection, or mismatched
  correlation id; and
- focused Core Host tests using fixture inputs only.

The integration may import the Phase 13.1 contracts and capabilities. It may
consume only already-sanitized, in-memory, test-owned objects. It must not
invoke lifecycle manager methods, launch a helper, read environment values,
read model/artifact/cache paths, touch Memory or SQLite, write files, export
telemetry, or alter product behavior.

## Allowed Implementation Surface

If approved, changes are limited to:

- `apps/core-host/src`: a provider-neutral Observability adapter/session file
  and export wiring if needed by local tests;
- `apps/core-host/test`: focused fixture-only tests for the adapter/session;
- documentation updates to this approval request with approval and verification
  evidence; and
- package build outputs only as generated by existing build commands, if any
  are already part of local workflow.

The implementation must not modify:

- `apps/core-host/src/file-system-model-lifecycle.ts` lifecycle semantics;
- Core Host provider registration or default composition;
- runtime helper process/session code;
- Memory, Memory SQLite, provider-vector retrieval/write/read paths;
- Desktop IPC, preload, UI, settings, provider visibility, or user commands;
- installer, updater, release metadata, or release channel behavior; or
- model artifacts, manifests, digests, caches, temporary runtime roots, or
  persistent storage.

## Data Boundary

The adapter may accept only these bounded report-shaped inputs:

- lifecycle operation status values equivalent to `passed`, `degraded`, or
  `blocked`;
- lifecycle cleanup status values equivalent to `not_started`,
  `not_required`, `passed`, or `degraded`;
- lifecycle rollback status values equivalent to `not_started`, `passed`,
  `degraded`, or `not_required`;
- a boolean previous-version preservation state;
- fixed lifecycle reason codes already used by sanitized lifecycle reports;
- helper health/load/release statuses represented only as fixed enum values;
- timeout/cancellation booleans or fixed stop reasons; and
- bounded opaque correlation IDs.

The adapter output must be a Phase 13.1 `ObservabilityObservation` or
`ObservabilitySummary` only. Unknown, missing, or unsafe inputs must produce a
sanitized blocked/degraded observation or a rejected result. Unknown errors
must map to `UNKNOWN_SANITIZED_FAILURE` without copying exception text.

## Sanitization Invariants

The implementation must:

- reject raw paths, URLs, credentials, signed URLs, environment values,
  digest values, model values, vectors, source text, raw helper output,
  exception messages, stack traces, arbitrary diagnostics, commands, scripts,
  cache paths, and artifact paths;
- keep observations in memory only and release/reset them on session release;
- deduplicate fixed reason codes and failure classes through the Phase 13.1
  collector;
- keep counters bounded by the Phase 13.1 contract;
- keep correlation identifiers opaque and not path-derived or source-derived;
- fail closed on unrecognized report shapes or enum values; and
- return only fixed reason codes, fixed failure classes, bounded counts,
  phase/status values, and booleans.

## Explicitly Not Authorized

This request does not authorize:

- unfreezing Model Lifecycle alpha or opening another lifecycle/runtime/cache
  acceptance window;
- running, loading, materializing, fetching, embedding, or releasing a real
  model;
- starting, reusing, warming, or inspecting a real helper session;
- reading local runtime, artifact, cache, Memory DB, or environment paths;
- creating persistent telemetry, logs, SQLite rows, metrics files, dashboards,
  alerting, network export, or product analytics;
- Memory routing, Memory writes, vector retrieval, SQLite migration, or
  historical indexing;
- provider registration, provider visibility, default opt-in, Desktop IPC,
  UI controls, settings, or user-facing commands;
- installer packaging, runtime bundling, automatic updates, release-channel
  exposure, product SLOs, or production-readiness claims; or
- using model, Memory, or observation output for shell, PowerShell, Windows,
  network, or tool execution.

Any future runtime use of the integration, telemetry persistence, UI display,
Desktop IPC exposure, helper instrumentation, Memory instrumentation, or
release behavior requires a separate exact-scope Product/Security/Release
approval.

## Required Tests

If approved, focused Core Host tests must cover:

- mapping a passed lifecycle report into sanitized Observability summary
  state;
- mapping degraded lifecycle health, activation, rollback, preservation, and
  cleanup outcomes into fixed failure classes and stop reasons;
- mapping helper health/load/release timeout, cancellation, and failure states;
- rejecting or degrading on unknown lifecycle/helper statuses;
- rejecting raw paths, URLs, credentials, digests, model values, vectors,
  source text, helper diagnostics, error messages, stack traces, env values,
  command/script fields, cache paths, and artifact paths;
- correlation mismatch and bounds enforcement; and
- session release/reset with no persistence.

The tests must use fixture objects only. They must not start Core Host as a
process, launch helpers, read env values, touch filesystem roots, access
Memory, or require model artifacts.
