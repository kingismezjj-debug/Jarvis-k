# Phase 14.2 Tool Execution Core Host Fixture Integration Approval Request

Recorded on 2026-08-06 after the Phase 14.1 provider-neutral Tool Execution
foundation landed and CI passed.

## Status

`APPROVED_IMPLEMENTED_AND_VERIFIED`

This request is for a narrow Core Host fixture-only Tool Execution integration
implementation wave. It does not authorize real shell, PowerShell, Windows,
process, filesystem, network, browser, clipboard, screen, model, helper,
Memory, SQLite, Desktop IPC, UI, persistent telemetry, default, installer,
update, release-channel, or model-driven tool invocation behavior.

## Context

Phase 14.1 added the provider-neutral Tool Execution alpha foundation:

- strict tool descriptors, bounded primitive tool arguments, and sanitized
  invocation requests in `@jarvis-k/contracts`;
- fixed lifecycle statuses, reason codes, failure classes, rollback/cleanup
  states, timeout/cancellation flags, bounded counters, and sanitized
  execution result envelopes;
- fail-closed fixture-only governance and execution in
  `@jarvis-k/capabilities`; and
- focused contract/capability tests proving that fixture execution returns no
  raw input, raw output, paths, URLs, commands, scripts, stdout/stderr, stack,
  env values, tokens, credentials, or process details.

Phase 14.2 is the proposed approval boundary for letting Core Host code
explicitly construct and use that fixture-only governance/executor in tests or
future already-approved developer-alpha diagnostic paths. The integration must
remain inert unless a caller imports and invokes it directly. It must not add
any user-facing route, IPC method, UI control, background job, provider
registration, default behavior, or real execution capability.

## Exact Scope Requested

Approve one implementation wave for:

- a Core Host fixture-only Tool Execution adapter/session that wraps the Phase
  14.1 `FixtureToolExecutor` and `decideToolInvocation` APIs;
- a small Core Host-owned fixture descriptor registry or caller-supplied
  descriptor/policy input, using only static test-owned fixture descriptors;
- explicit session methods for policy evaluation and fixture execution that
  return only Phase 14.1 sanitized decision/result envelopes;
- fail-closed handling for unknown tool IDs, malformed descriptors, malformed
  requests, blocked tools, missing confirmation, disabled fixture execution,
  unavailable fixture implementation, timeout/cancellation simulation,
  sandbox/scope violation, rollback failure, cleanup failure, and
  sensitive-output simulation;
- optional mapping from a sanitized tool execution result into an already
  in-memory Observability collector only if it consumes fixed report-shaped
  values and does not create telemetry persistence;
- focused Core Host tests using deterministic fixture objects only; and
- documentation updates to record approval and verification evidence.

The adapter may import `@jarvis-k/contracts` and `@jarvis-k/capabilities`.
It may consume only static in-memory fixture descriptors, fixture policies,
and bounded fixture invocation requests. It must not discover tools from the
host, inspect the operating system, read environment values, read or write
files, access Memory or SQLite, start helpers, load models, call network APIs,
spawn processes, or expose anything through Desktop IPC or UI.

## Allowed Data Boundary

The adapter may accept only these bounded in-memory inputs:

- Phase 14.1 static `ToolDescriptor` objects; `execution="fixture"` is the
  only executable mode, while valid non-fixture descriptors may be supplied
  only to prove fail-closed policy decisions in tests;
- Phase 14.1 `ToolPolicy` objects with `windowsExecutionEnabled=false`,
  `networkAccessAllowed=false`, and `shellExecutionAllowed=false`;
- Phase 14.1 `ToolInvocationRequest` objects whose input values pass the
  bounded primitive argument schema;
- explicit boolean confirmation input;
- explicit deterministic fixture simulation options for unavailable fixture,
  timeout, cancellation, sandbox/scope violation, rollback failure, cleanup
  failure, and sensitive-output detection; and
- bounded opaque correlation/session IDs if needed for in-memory test-only
  grouping.

The adapter output may contain only Phase 14.1 `ToolPolicyDecision` and
`ToolExecutionResult` envelopes, plus optional fixed Core Host wrapper fields
such as `accepted`, `toolCount`, or `sessionReleased`. It must not add raw
tool input, raw tool output, stdout/stderr, paths, URLs, credentials, signed
URLs, tokens, env values, commands, scripts, exception messages, stack traces,
process IDs, hostnames, usernames, tester IDs, model IDs, digests, vectors,
source text, Memory records, helper diagnostics, or raw diagnostic payloads.

## Required Safety Invariants

The implementation must preserve these invariants:

- fixture execution is the only executable mode;
- unknown, malformed, blocked, unallowlisted, unpermissioned, disabled,
  Windows, shell/process, filesystem, screen, clipboard, and network-like
  tools fail closed before execution;
- confirmation-required tools return `needs_confirmation` until explicit
  confirmation is supplied;
- timeout, cancellation, sandbox, rollback, cleanup, and sensitive-output
  cases are deterministic fixture simulations, not real timers or side
  effects;
- adapter/session release clears in-memory state and never persists reports;
- no model, Memory, helper, runtime, OS, filesystem, network, browser, IPC, UI,
  or telemetry sink is touched; and
- serialized reports remain sanitized and bounded.
